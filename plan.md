## Phase context

Active delivery phase `phase-2` only. Later phases start automatically after QA `all_passed` (or use `gt rig set-phase` to switch manually).

- Phase verification: `cd taskboard && python -m pytest -q tests`

## Phase-2 implementation contract

This phase extends only the canonical files listed in the active delivery
profile. No duplicate module, alternate route, second page, or phase-3 file
may be added. The task repository work remains in
`taskboard/repository.py`, validation and row mapping remain in
`taskboard/models.py`, and HTTP wiring remains in `taskboard/main.py`.

The repository test bead must cover the architecture-owned task operations:
`TaskRepository`, `list_tasks(project_id, status=None, priority=None)`,
`create_task(...)`, `update_task(task_id, changes)`, and
`delete_task(task_id)`. It must preserve project behavior and prove task
defaults (`todo` and `medium`), UTC timestamps, ascending IDs, status and
priority filters, combined-filter AND semantics, partial updates that preserve
omitted fields, and project-delete cascade behavior.

The API test bead must exercise the exact task routes from SPEC:
`GET /api/projects/{project_id}/tasks`,
`POST /api/projects/{project_id}/tasks`,
`PATCH /api/tasks/{task_id}`, and
`DELETE /api/tasks/{task_id}`. Assertions must cover documented 200, 201, and
204 responses, empty arrays and bodyless deletes, task JSON fields, invalid
title/description/status/priority values, empty PATCH payloads, missing
project/task 404 responses, application error objects, and preservation of
the phase-1 health and project tests. Both list filters must be tested
together as an AND query.

The template bead owns the single page's accessible project selector, project
form, delete-project control, task form, filter controls, three visible
columns headed `To Do`, `Doing`, and `Done`, and loading, empty, and error
regions. The JavaScript bead consumes those hooks and the exact API contract:
it loads and selects projects, creates and deletes projects, loads and
creates tasks, edits title/description/priority, deletes tasks, and advances
status exactly todo to doing to done. Done cards hide or disable Move forward.
It must use `textContent` and `replaceChildren` for user-controlled content,
use `window.confirm` for project deletion, and visibly report API failures.
The CSS bead is presentation-only and supplies readable responsive columns,
cards, controls, focus states, and status messages.

The fixture bead must continue to call
`taskboard.main:create_app(db_path: str | None = None)` with an explicit
temporary SQLite path per test and must never use the runtime fallback
database. The content-test bead must assert real root HTML with the heading,
both forms, project-selection hooks, all three column headings, and nonempty
static responses; it is not a substitute for repository or API behavior
tests.

## Dependency order and verification

Implement tests against the existing phase-1 application before completing
the browser integration. The template supplies hooks consumed by
`taskboard/static/app.js`; the JavaScript consumes the routes owned by
`taskboard/main.py`; the fixture is consumed by both API and repository
tests; and the CSS consumes template selectors. The active phase verification
command is exactly:

    cd taskboard && python -m pytest -q tests

The gate requires persisted create, edit, move, filter, and delete behavior,
exact documented routes and response shapes, safe user-content rendering, and
all existing phase-1 assertions. Playwright manifests, npm files, browser
runner configuration, and other phase-3 deliverables are explicitly outside
this phase.
